# Cuotai Desktop (Tauri 2)

Cross-platform front end: main window + tray popover + Settings window. No npm or bundler:
the UI is plain HTML/CSS/JS in `ui/` and the shell is Rust in `src-tauri/`. It only reads `cuotai-core`.

**Settings window (PRD 0020 RF1, RF2):** `ui/settings.html`, label `settings`, created on demand by the `open_settings { page?, anchor? }` command (`src/settings_window.rs`) and destroyed on close; a second request focuses the open window and tells it to read the new target (`settings-navigate`, then `settings_target`). Every entry point uses it: the gears of the main window and the tray popover, the tray menu, the macOS app menu item `⌘,` (`Ctrl+,` in the windows elsewhere) and the links in other screens (for example the Local cost page from the cost details). Its last size and position are kept in `desktop.json` (`settings_window`, logical pixels; dropped when off every screen). The sidebar comes from one registry, `ui/js/settings/registry.js` (page id, icon, label key, order, the sections each page holds); each page is a module under `ui/js/settings/` with `html(ctx)` and `bind(root, ctx)`, loaded only when shown. A change made there is broadcast as `settings-changed` so the main window and the tray repaint; the preferences mirrored in `localStorage` (theme, language, order, grouping, pace, animations) also reach them through `storage` events. `scripts/test-settings-window-ui.mjs` checks the page order, the navigation and that every control of the old dialog renders on its page. The browser demo opens `settings.html` directly (`?page=…&anchor=…`).

The 5-hour/weekly windows and the exclusion of rate limits from the summary use the core's `Metric.kind` and `Metric.window` directly; neither the shell nor the JS classifies metrics from the text of `label` or `period`.

```sh
cd apps/desktop/src-tauri
cargo run                 # development
cargo install tauri-cli   # optional, for packaging
cargo tauri build
```

Config: `CUOTAI_CONFIG` > the file chosen in **Settings › Advanced › Files** (stored in `desktop.json`, never in the TOML) > `<OS config dir>/cuotai/config.toml`; the desktop app never reads `./cuotai.toml` from the current directory. To see the same accounts as the TUI, choose the same `cuotai.toml`; **Use system default** goes back to the OS path. Switching the file reloads the accounts through the core and discards the previous configuration's state. The effective path is shown with its origin (variable, chosen or system default). If the file does not exist, the first `Save` creates it with 0600 permission.
Different-files warning: each front end records the last opened file in `<OS data dir>/cuotai/last-config-*.json` (only the normalized path and the date). If the TUI used another file, the dashboard and **Settings › Advanced › Files** show both paths and remind you that accounts and model caches are separate; to align them, choose the same file in Settings.
About: **Settings › About › Open-source libraries** opens with a special thanks to the projects created by Brazilians (Dracula and Tauri) and lists the direct dependencies, the visual assets and the open palettes of the themes (license, the component that uses each and its repository), the same list as the TUI (`?`), maintained in `cuotai_core::about`. Each repository opens in the browser through the `open_external` command, which only accepts addresses from that list.
Themes: tokens in `ui/css/themes.css`, one file per theme in `ui/css/themes/` (contract and palettes in its `README.md`) and the registry in `ui/js/themes.js`; the built-in **Cuotai** theme is the app's own pastel palette, and the default is Dracula.

On the dashboard, **Add account** or **Edit** opens the form. Choose **Browser sign-in** (or **AWS SSO** / **Bailian console**, depending on the provider) and press **Sign in**. For Kiro, choose the method, region and start URL when using Identity Center; each account must be authorized separately. The dialog shows the URL and the device code to copy; Xiaomi MiMo also accepts the pasted code of the current attempt. **Cancel sign-in** stops the wait before anything is written. **Save** persists the OAuth credential in the OS vault and the account in the TOML; a write failure keeps the authorization in memory so you can try again. The AWS CLI and `bl` keep their own credentials outside the Cuotai vault. The modes, the flow options and the registration fields (`client_id`/`tenant`, ...) come from the core's descriptors; the desktop app only renders them.

On the dashboard, drag the card handle, use the move-account arrows, or focus the handle and press ↑/↓. The new order is written to `cuotai.toml`, shared with the TUI, and does not start any provider query; each account's comments are kept.

**Remove account** opens a dialog: for accounts with a saved OAuth credential, choose **Remove and keep in vault** or **Remove and delete from vault**. The TOML is always saved first; the vault purge runs afterwards and, if it fails (vault unavailable) or is refused because another surviving account shares the credential, the dashboard warning includes a **Try to delete the credential now** button that re-runs the purge against the current configuration (it deletes the credential once the surviving account is also removed; it deletes nothing while the surviving one exists). Recovery uses an opaque identifier kept in memory until the purge succeeds, and it is discarded on any configuration reload.

**Models (PRD 0002 RF6):** the account details (window and popover) and the edit form have a **Models** section: local search by ID/name (`↓` enters the list; `↑`/`↓`/`Home`/`End` navigate; `Esc` goes back to the search), announced progress (`aria-live`) and **Sync models**, disabled while the operation runs. The first query happens only when the section is opened with nothing recorded; reopening, searching or restarting uses the core cache (`models.sqlite3`, shared with the TUI for the same `cuotai.toml`), never `localStorage`. A failure or interruption shows the error/date and keeps the previous catalog; a provider with no contract shows the reason, with no network request. When creating an account, choose an already configured account of the same provider to see its catalog; with none, the core's guidance appears. Commands: `model_state`/`load_models`/`sync_models` (`{ index, generation }`, they return `ModelState`) and `model_support` (`{ provider }`); `generation` comes from the `View` and changes on every save/remove/move/reload/file switch, so a result from an old generation fails with `"stale"` and is discarded, never assigned to the new index. The browser demo shows only an explicit demonstration state.

**History (PRD 0006 RF5):** the account details window has a **History** section with **24 h**, **7 days** and **30 days**: per recorded metric, its lowest, highest and last value and a compact area chart with the last reading highlighted, a dashed marker at each reset and gaps where nothing was recorded (the app closed, the computer off). Screen readers get an equivalent table of the window instances instead of the chart; the chart's entrance follows the motion setting and `prefers-reduced-motion`. An account with no recorded reading in the span explains that the chart fills in as readings are recorded. **Settings › Data & privacy** turns recording on or off (on by default, saved in `desktop.json`; off keeps what was recorded until you erase it, still pruned by the retention, and the TUI/CLI keep recording), shows the size of the history file on disk, and keeps the retention, export and erase controls. The browser demo (`js/lib.js`) draws ten synthetic days with a missing day.

**Local server (PRD 0012 RF5):** **Settings › Advanced › Integrations** starts the core's read-only local server inside the app (off by default; `serve` in `desktop.json`): `127.0.0.1` on exactly the chosen port (6738 by default, 1024–65535), serving this app's own refresh cycle, never querying per request. The section shows the effective address or why it is not serving (a taken port names another Cuotai server such as `cuotai --serve` when it is one; the main window shows a banner too), generates, copies (never displays), renews and revokes a bearer token kept in the system vault, turns "allow browsers" on only after its warning is confirmed, and offers "Share usage statistics" (`serve.stats`, off by default) to also serve `/v1/stats`, which the server answers only with the token (PRD 0031 RF11.2.5). See [`docs/local-server.md`](../../docs/local-server.md).

**Hooks (PRD 0013 RF4):** **Settings › Advanced › Integrations › Hooks** (`src/hooks.rs`) edits the `hooks.toml` beside the loaded accounts' TOML through the core's `hooks::Document` (validated, saved only over the revision shown, comments of kept rules preserved) and runs the confirmed rules with the core's `hooks::Runner` over the `export::v1` of this app's own refresh cycle (every `Backend::emit` feeds the core's `watch::Watcher`; no query). Off by default (`hooks` in `desktop.json`); turning it on or saving changed rules while on opens a dialog with the core's exact listing, and the confirmation is the core's `Consent`, shared with `cuotai --watch --hooks`. A file changed since its confirmation stops the rules before they run again (Settings asks again; the main window shows a banner). **Test** sends a running rule its `Rule::sample`; **Latest runs** reads the shared `runs.log` (`RunLog::latest`), repainted on the `hooks` event after each run. See [`docs/events.md`](../../docs/events.md#hooks-in-the-desktop-app).

**Configuration conflict (RF4):** if `cuotai.toml` changed on disk since it was loaded (external edit, `git pull`, a second process), the next **Save** refuses to write and shows the typed message `edit_error.conflict` with a **Reload file from disk** button. Reloading reopens the file, rebuilds the monitor/schedule/tokens, discards the recovery identifiers (they refer to the previous configuration) and keeps the dialog draft ready for another attempt. The same cheap detector runs when the window gains focus and before the account editor opens, offering **Reload now** or **Keep editing**. Validation errors (empty field, duplicate name, invalid interval, invalid option) land automatically on the matching field (`name`, `credential`, `params.<key>`, `interval`, ...) instead of only a global warning.

**Dependencies with a security advisory:** Tauri 2's Linux stack (gtk/webkit2gtk 0.18) pins `glib` 0.18, which is affected by [GHSA-wrw7-89jp-8q8g](https://github.com/advisories/GHSA-wrw7-89jp-8q8g) (unsound `VariantStrIter`); the fix only exists in `glib` 0.20 and no stable Tauri 2 release adopts it. Neither the app nor its dependencies use `VariantStrIter`/`Variant::array_iter_str`, and on macOS/Windows the crate is not even compiled. The `tests/glib_advisory.rs` test fails if that usage appears while an affected `glib` is in `Cargo.lock`; reassess when upgrading Tauri.

## Adding a setting (PRD 0020 RF11)

Every setting is one row of the Settings window (`ui/js/settings/`). To add one:

1. **Choose the page** in `registry.js` (General, Dashboard, Alerts, Data & privacy, or one of the Advanced pages). A page with more than 8 rows shown must put the rest in a disclosure (`disc()`) or a sub-page (`subRow()` and `subpage()`). A new page is a `PAGES` entry plus a module exporting `html(ctx)` and `bind(root, ctx)`, and its decision is recorded in PRD 0020 or its successor.
2. **Define the row** in that page's module with `row({ key, label, desc, info, control })` from `rows.js`: a short label (at most four words), at most one description of 90 characters, the long text behind `info`, and one component (`sw`, `seg`, `select`, `num`, `buttons`, `pathHtml`). Every string is a catalog key in all four files of `ui/locales/`.
3. **Make it searchable:** add `settings.kw.<key>` (a handful of synonyms, in each language) to the four catalogs. A row without keywords fails `scripts/test-settings-search-ui.mjs`; a page whose rows come from the shell's state exports `searchHtml()` so the index sees them.
4. **Bind it** in `bind()`: the value saves on change (or on Enter/blur with `commitField`), shows the "Saved" toast, and a refusal shows the core's message in the row (`rowError`). Business rules and validation live in the core or the shell command (`src-tauri/src/settings.rs`), never in the page. A preference that other windows must follow is stored in `desktop.json` through `set_preference` (add the key and its validation in `settings.rs`); the shell broadcasts `settings-changed` and each window re-reads.
5. **Add it to the parity checklist** (`CONTROLS` in `registry.js`) and run `node scripts/test-settings-window-ui.mjs` and `node scripts/test-settings-search-ui.mjs`.
