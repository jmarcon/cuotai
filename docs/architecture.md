# Architecture, Rust Library and Verification

## Core / TUI / Desktop split

```text
crates/cuotai-core/       Rust library: accounts and persistence, credentials, providers, metrics, queries
crates/cuotai-tui/        cuotai binary: CLI, sign-in wizard, Ratatui, keyboard/mouse
apps/desktop/             Tauri 2 app: main window, tray popover and native menu
```

`cuotai-core` is independent of any UI (it depends on neither Ratatui, Crossterm nor a graphical loop):

- **`access`**: `describe(account)` returns, with no network and without reading credentials, how the account's usage is read: `level` (`Official`: an interface the vendor documents for that credential, always with a documentation URL; `Undocumented`: internal or inferred, may change without notice; `Derived`: inferred from Cloud Monitoring metrics or rate-limit headers; `Unavailable`: no query, always with a `reason`), `credential` class, optional `plan_requirement`, `scope` (`Account`, `Organization`, `WholeCloud`, `Product`), `metered` (`Provider::is_metered`), `evidence` (documentation URL or 9router/community-client file) with `verified_on`, and localized `summary`/`credential_hint`/`risk` (`access.*` ids). The `match` on `Provider` is exhaustive with no wildcard, so a new provider does not compile without declaring its access; `product`/`query_mode`/`mode`, the native login and `session_env` select the variant. `UsageAccess::explain(&report)` is what cards and details show in place of a failed report's generic note: the reason of an `Unavailable` account, or `access.interface_changed` (with the evidence URL) for an `Undocumented` account whose report is `Error` with `query.schema`; `None` otherwise. `UsageAccess` serializes with snake_case slugs (`level`, `credential`, `scope`) and `evidence` as `{ "kind": "documentation" | "reference", "url" }`, the shape `export::v1` (PRD 0012) embeds per account; it never enters `Report`, `Snapshot` or `--json`.
- **`account_edit`**: `field_descriptors` and `native_option_descriptors` define fields, options and which of them are required per provider; `visible_field_indices` decides which fields apply for a given product, mode and login; `build_account` validates a draft against that schema; `draft_access` describes the draft with the `access` rules (the editors' level, notes from `UsageAccess::notes`, cost warning from `cost_advisory` and "Save anyway" text from `save_confirmation`); `Config::upsert_account`/`without_account` create, edit or remove accounts.
- **`alerts`**: usage threshold alerts (PRD 0008). `evaluate(prev, next, &prefs, &state, now)` is pure (injected clock, no query) and returns the `AlertEvent`s a new reading deserves (account key, metric label and window, `kind` `Threshold`/`Exhausted`/`Recovered`, `threshold` in percent, `consumed` fraction, `resets_at`). Only a `Quota` with a positive finite cap counts; uncapped metrics, `Balance`, `Credits`, `Spend`, `Usage`, `RateLimit` and missing or non-finite values never fire. `AlertPrefs` (off by default) holds the thresholds, 10 to 99% (`ThresholdError` otherwise; 75 and 90 by default); exhaustion is always evaluated while it is on. A window instance is the metric's `resets_at` within `resets::DRIFT_TOLERANCE` (2 minutes); in one instance each level fires once, a query crossing several emits the highest, and a level re-arms only after consumption falls `HYSTERESIS_POINTS` (5) below it or in a new instance. `Recovered` fires once, in the first later instance with slack, and only after the exhaustion was notified. Nothing fires without a usable `prev` (same account, `Ready`, older) or for a reading older than `CROSSING_GRACE` (10 minutes); on an account's first reading in the process `prev` (e.g. the last reading PRD 0006 recorded) must be at most that much older, and only levels it had not reached yet in the same instance count as crossed. After delivering, `AlertState::update(next, &prefs, &delivered, now)` records every level the reading reached (notified or not, so a crossing seen silently is never notified later), re-arms and follows `resets_at` drift; `retain_accounts(keys)` forgets removed accounts. The state holds digests of the account key and metric label, thresholds and dates only.
  - **Delivery and preferences (PRD 0008 RF2, RF3):** `AlertPrefs` also holds `exhaustion` (off: reaching 100% notifies the highest threshold instead), `recovery`, `muted_accounts` and `muted_metrics`; `wants(event)` is the filter `evaluate` applies. `AlertState` serializes its marks (never the first-reading set) into `resets::Ledger` (`alerts`/`alerts_mut`, the `alerts` key of `notified.json`), `prune(now)` drops marks older than `LEDGER_KEEP`, `update` and `retain_accounts` return whether the persisted part changed, `active(report)` lists the metrics with a notified level in their current window and `eligible(metric)` says whether a metric can alert. `notice(groups, now, tz)` writes one notification for the events of one or several accounts (`alerts.*` ids) and `NOTICE_SPACING` (1 minute) bounds how often front ends send one. The desktop backend judges each report against the reading it replaces before `RefreshCycle::finish_account`/`finish_full` and records the events only when the cycle accepted it; `Notices::tick` (`apps/desktop/src-tauri/src/notify.rs`) delivers them, one notification per account, the excess grouped, with the preferences in `desktop.json` (`alerts`). The TUI with `--notify` (PRD 0008 RF4, `crates/cuotai-tui/src/notify.rs`) follows the same order with the default `AlertPrefs` switched on and a session-only `AlertState` (never saved), and shows each account's `notice` in its header banner with one `BEL` per pass.
- **`config_file::ConfigFile`**: discovers, loads and atomically writes the TOML, preserving comments and rejecting concurrent external edits.
- **`cost`** (PRD 0015 RF1–RF3): local usage from the session logs of command-line tools, off by default and independent of the `Monitor`. `SettingsStore` (`<OS local data dir>/cuotai/cost/settings.json`, `0600`) keeps per source the consent, as the digest of the `Disclosure` the user accepted (exact directories, file pattern, purpose, what is extracted and never read), chosen directories, the `Period` and the `Retention` (120 days, 7 to 730); a source is on only while its consent matches what it would read now. Each source is an adapter behind the crate-private `Source` trait (`id`, `default_roots`, `pattern`, `is_log`, `parse`; `claude.rs`, `codex.rs`) whose parser deserializes only the time, the model, the token counts and the session identifier (kept as a digest), skipping and counting invalid lines. `Scanner::scan(now)` walks the roots of the sources that are on (no symbolic links, only the user's regular files, `RootState::NoAccess` instead of any workaround), reads only complete new lines within `Limits` and writes each file's chunk into `CostIndex` (`cost.sqlite3`: usage per source, local day, model and file digest, anonymous sessions, request digests for dedup, per-file control) in one transaction that checks the source is still on; a shrunk or replaced file first loses its share. `CostWorker` runs it on its own low-priority thread every 5 minutes, sooner while a limited scan left work behind, pausing in energy-saving mode (`cost::energy_saving`); `turn_off` and `CostIndex::erase` remove everything derived. The TUI (`crates/cuotai-tui/src/cost.rs`, the `--cost-*` flags) and the desktop (`apps/desktop/src-tauri/src/local_cost.rs`, Settings → Local cost) start the worker beside their refresh cycle and drive the consent, the options and the erasure. Prices (RF3, `prices.rs`): `PriceTable::embedded()` (`prices.json`, USD per million tokens with an effective date and a source) under the user's manual `pricing.json` (`PricingFile`, validated as a whole; an invalid one is ignored with a `PricingError`), looked up in `Prices::price` by exact or undated model name, user first; `estimate.rs` holds the pure `cost::estimate(&[DailyUsage], &Prices) -> Estimate` (integer pico-dollar sums, `Usd` rounded half up when read, unknown models never zero, the unknown share, the tables used and the "not a charge" notice).
- **`events`** (PRD 0013 RF1): `diff(prev, next, &mut state, now)` compares two consecutive `export::v1::AccountExport`s of one account and returns the edge `Event`s of [`events.md`](events.md) (`quota_threshold_crossed`, `quota_exhausted`, `quota_recovered`, `quota_reset`, `account_blocked`, `account_unblocked`, `refresh_failed`, `refresh_recovered`, `auth_required`, `provider_incident`, `usage_updated`). Pure (injected clock, no query), it reuses `alerts::evaluate` for crossings, exhaustion and recovery, `resets::passed` (the reset planner's eligibility and drift identity) for window resets, `metrics::binding` for blocking and the provider status for incidents. `EventState` keeps in memory only each account's last status, last `Ready` reading, binding metric, last reported usage (`usage_updated` at most once per 600 s) and the alert marks; the first reading is a baseline and a new state (a restart) builds new ones. A failure is a `FailureCategory` (`timeout`, `offline`, `auth_required`, `rate_limited`, `schema_changed`, `provider_error`) decided by the status and the note id (`query.timeout` since 0.53.0 tells a deadline from `query.transport`); payloads never carry notes, URLs, credentials or raw messages.
- **`export::v1`**: `Export::from_cycle(config, identity, cycle, incidents, now, options)` builds the versioned export contract ([`export-v1.md`](export-v1.md)) from the state a `RefreshCycle` already holds and the provider statuses already read (`Monitor::incident_statuses`), without querying: per account its `key`, `class`, the current `report`, `age_seconds`/`freshness`/`clock_adjusted`, the preserved `last_good` reading with `stale`, `binding`, `pace` per metric, the `access` descriptor and the provider's `incident` (PRD 0011 RF5; `null` while status queries are off). Notes and `source` are redacted (credential variable names, URL credentials and queries, and e-mails unless `Options::include_identity`); missing values stay `null`. A reference-file test and a JSON Schema test guard the contract. `ConfigIdentity::digest` is the configuration key it publishes (and `models` stores).
- **`headless::Driver`** (PRD 0012 RF4, PRD 0013 RF2): the refresh loop of a front end without a screen. `Driver::new(config, monitor, now)` builds a `RefreshCycle` with the recorded readings restored; `step(now)`, called every `TICK` (250 ms) with the caller's `Instant`, hands finished queries to the cycle and starts what is due (the first full sweep, pending and periodic accounts with the cycle's backoff, the provider status every `STATUS_TICK` while status queries are on) and says whether something finished. `cycle()` is shared with other consumers (the local server), `export(config, identity, now)` builds `export::v1` from it, `ready_seen()` and `failing()` feed the exit codes, and dropping it abandons the queries in flight. `cuotai --serve` and `cuotai --watch` share one driver (`crates/cuotai-tui/src/headless.rs`), so watching and serving never add a query.
- **`history`**: local measurement history (PRD 0006). `Monitor::with_history(store)` records every `Ready` report through `HistoryRecorder` (a worker thread behind a bounded queue: the refresh only enqueues, a full queue drops and counts the reading; `HistoryStatus::warning` carries storage failures, ceiling pruning and drops to the front ends), which also prunes by `Retention` on open and every 24 hours (age, hourly reduction after 7 days keeping window peaks, 64 MiB ceiling); `restored_readings` feeds `RefreshCycle::restore_last_good` on opening and `recent_points` the pace's recent slope; `export`, `erase_account` and `erase_all` serve the desktop's Settings → History. `HistoryStore::in_data_dir(&file)` uses `<OS local data dir>/cuotai/history/history.sqlite3`, a file of its own (directory `0700`, file `0600` on Unix, even if they already existed), opened per operation in WAL mode with a busy timeout so the TUI, the desktop app and the CLI on the same TOML write to it at once. Rows are keyed by the digests `models` uses (configuration and account identity: a move keeps the series, a rename or a new credential, product or region starts another) and hold only numbers and window metadata plus the metric label; never secrets, account names, URLs or notes, and a missing or non-finite value is `NULL`. `record` is idempotent per account, metric (`metric_key`: digest of kind, window, label and unit) and time; `mark_removed(&saved, now)` marks the series of accounts gone from the TOML for pruning. `latest` (the last reading per metric with its original time), `series` (`pace::Point`), `windows` (a window ends on a drop above 20% of `limit` or a `resets_at` move beyond 2 minutes) and `bounds` never touch the network. The schema is versioned (`PRAGMA user_version`, forward migrations; a newer file is rejected) and every storage failure is `HistoryError::Storage`.
  - **Views (RF6):** `HistoryStore::account_history(account, range)` (also `Monitor::account_history(index, range)`) returns every recorded metric of an account with samples in the span as `MetricHistory` (points with a finite `used`, window instances, last limit) in one query, without creating the file; `MetricHistory::trend()` gives the lowest, highest and last value and `levels(start, end, cells, levels)` the sparkline levels (bucket peaks, zero-to-limit scale or lowest-to-highest without a limit, `None` for gaps), so the TUI details (`HistoryRange` 24 h / 7 d / 30 d) and `--history` only map them to glyphs and text.
  - **Desktop chart and switch (RF5):** `MetricHistory::chart(start, end, cells)` places the area chart the desktop details draw (`Chart`: axis `floor`/`ceiling`, per-bucket peak heights from 0 to 1 joining samples up to an hour apart and leaving longer silences as gaps, the last point and a `ChartReset` where each window instance after the first began); the Tauri command `account_history(index, generation, range, metric_key)` returns it with the window instances, guarded by the view's generation like the model commands. `Monitor::set_history_recording` (from `desktop.json`) makes the recorder ignore new readings while keeping the data, and `HistoryStore::size_on_disk` reports the file with its WAL for Settings → History.
- **`incidents`**: public provider status (PRD 0011). `source(provider)` is the pure, exhaustive registry of verified sources (format, URL, component scope, verification date; `None` when unverified). `Monitor::incidents()` is the `IncidentMonitor` holding the opt-in preference (off until `set_enabled(true)`) and one cached reading per URL, shared by `with_config` and transferable with `with_incidents`. `Monitor::refresh_incidents` (also run by `refresh`) queries the configured providers' due sources once per URL every 5 minutes through the monitor's HTTP client and semaphore, without credentials, with a 5 s timeout and a 1 MiB cap; `incident_statuses` returns the cached `ProviderStatus` (normalized `IncidentState`, sanitized active `Incident`, page URL, `read_at`, `stale`). A failed query (`error`, `rate_limited`, `authentication_error`) during a `degraded`-or-worse state gains `note.incident.ongoing` (plus `note.incident.auth_wait` for authentication) without changing its `Status`. See [`providers.md`](providers.md#status-client-since-0470).
  - **Desktop (RF4):** `Monitor::status_domains()` lists the hosts the configured providers' sources reach (no network, also while off) for Settings → Privacy, `IncidentState::label()` gives the `incident.state.*` badge text, and `incidents::is_status_link(url)` is the allow-list `open_external` uses for status and incident pages. The desktop backend keeps one `IncidentMonitor` across reloads (`status_queries` in `desktop.json`, off by default), runs `run_incidents` beside the scheduler and repaints the tray icon with an outage dot while a provider is in a partial or major outage.
  - **TUI and CLI (RF5):** `--status` or `CUOTAI_STATUS=1` enables the `IncidentMonitor` (`--no-status` wins), which the TUI carries into every rebuilt monitor; the event loop spawns `refresh_incidents` every 30 s and renders the returned statuses (card badge, details block), and `--once` prints a line for a flagged provider from `incident_statuses`. `export::v1::Export::from_cycle` takes those statuses and publishes each account's `incident`.
- **`Monitor`**: `refresh` and `refresh_account` query providers and normalize reports; the internal semaphore limits full and single-account queries together (1–32), applies a per-account deadline (1–300 s), preserves the configured order and isolates failures per account.
- **`models`**: per-account model catalog, outside the quota refresh. `Monitor::with_model_cache(ModelCache::in_data_dir(&file))` writes to `<OS persistent data dir>/cuotai/models/models.sqlite3` (outside any cache folder, separate from the TOML, the vault and the debug credential SQLite; directory `0700` and file `0600` on Unix, even if they already existed). Each row stores digests only: SHA-256 of `ConfigFile::identity()` and of the account identity (provider, name, `credential_env`/`oauth` and `params`, except `models` and `billing_cycle`, which only filter or date the quota); never secrets, HTTP bodies or URLs. Moving an account keeps its entry; renaming it or changing its credential, product or region creates another one. `Monitor::prune_models` deletes configuration entries that are absent from the freshly loaded or saved TOML (the TUI and the desktop app call it on open, on saving an edit and on removal), without touching live accounts of another window. States: `not_fetched`, `fetching`, `ready`, `failed`, `interrupted`, `unsupported`. `model_state` only reads; `load_models` queries only when no attempt is recorded (success, empty list, failure or interruption are stored and not repeated); `sync_models` queries and, if it fails, keeps the previous catalog with its date. Every query needs a per-account claim (owner token + lease = account deadline + 30 s) taken in `BEGIN IMMEDIATE`: another window or process with a live claim does not query and instead waits for the stored result (100 ms polling, bounded by the lease), so simultaneous syncs become a single request; only the owner publishes, so a stale completion never overwrites a newer result. Cancellation expires the lease immediately and a killed process lets the lease run out: in both cases the row becomes `interrupted`, with no partial list and no automatic retry, until a manual `sync_models`. A persistence error is `ModelError::Storage`. Today every provider except Alibaba Cloud tries to list models, either live with the account's credential or from a built-in list that is labelled as not being a query of the account; see the matrix in [`providers.md`](providers.md). `Unsupported` makes no network request.
- **`refresh::RefreshCycle`**: computes the effective deadline of each account (including a 300 s floor for providers billed per query, such as AWS Bedrock) and assembles the `Snapshot` incrementally. After `RateLimited`, `AuthenticationError` or a task failure, the account's interval doubles on each consecutive failure up to 1 h (configured intervals above 1 h are kept, never shortened); a result with any other status restores the configured interval. Manual refreshes remain available. `finish_account` and `finish_full` return whether the result was accepted (a stale generation is dropped).
- **`serve`** (feature `serve`, off by default; PRD 0012 RF2/RF3): `LocalServer::start(ServeConfig, source)` serves `GET /health`, `/v1/snapshot`, `/v1/accounts/{key}` and `/v1/limits` ([`local-server.md`](local-server.md)) from a `Source` closure that builds `export::v1::Export::from_cycle` from the front end's `RefreshCycle`, so no request queries a provider (`503` with `Retry-After` before the first reading). HTTP/1.x parsing uses `httparse`, one request per connection with JSON and `Cache-Control: no-store` on every answer, bounded connections, head and URL sizes and time (`Bounds`). Loopback bind unless `allow_non_loopback` (which needs a token), loopback `Host` only (DNS rebinding), browser `Origin`/`Sec-Fetch-Site` refused unless `allow_browsers`, optional bearer `Token` kept in the OS vault (`SystemTokenVault`, `ensure_token`), an `AccessEntry` log without headers or query; port 6738 with fallback to the next nine. The crate's own tests enable the feature through a self dev-dependency; `cuotai-tui` turns it on for `cuotai --serve` (PRD 0012 RF4): `crates/cuotai-tui/src/serve.rs` serves the cycle of the core's `headless::Driver`, like the dashboard's scheduler (a first full sweep, then the per-account deadlines and backoff of the core), and the server's source reads it.
  - **Desktop (RF5):** the desktop turns the feature on for Settings → Integration (`apps/desktop/src-tauri/src/local_server.rs`). It creates no second cycle: on every state change (`Backend::emit`) while the server is on, the backend publishes a `Feed` (the configuration, its identity, a copy of the live `RefreshCycle` and the provider statuses it just showed) and the source builds the export from it per request. `desktop.json` keeps `serve` (`enabled`, off by default; `port` 1024–65535, 6738 by default, bound exactly with `port_fallback` off; `allow_browsers`; `token`, which only says a token in `SystemTokenVault` is required, so a missing or unreadable one keeps the server off). Each change restarts the server, whose state (`off`, `on` with its URL, or `error` with the core's `ServeError` text) reaches Settings and a main-window banner; on `PortInUse`, `serve::is_cuotai_server(port)` asks that port's `/health` once (1 s) and recognises another Cuotai server (`cuotai --serve`) by its answer or its `401` with Cuotai's bearer realm.
- **`watch`** (PRD 0013 RF2): `Watcher::new(state, selected).observe(export, now)` runs `events::diff` per account between consecutive exports (the first export of an account is its baseline, an account gone from the export is forgotten) and keeps only the selected `EventKind`s, whose state still moves. `parse_events(names)` accepts the payload names (`watch.error.unknown_event` lists them otherwise); `with_interval(config, seconds)` refreshes every account without its own `refresh_seconds` every `seconds` for one run (60 to 86 400, `watch.error.interval_range` otherwise; never below 300 s for a provider billed per query). `Event::summary()` is the readable `events.summary.*` line.
- **`hooks`** (PRD 0013 RF3): `Hooks::load(path)` validates `hooks.toml` (next to the accounts' TOML, `Hooks::path_beside`; `deny_unknown_fields`, a `command` argument vector whose program is absolute or a bare `PATH` name, `timeout_seconds` 1–60, errors as `hooks.error.*` naming the line or rule). `Consent` keeps `{identity digest of hooks.toml → SHA-256 of the rules}` in `<data dir>/cuotai/hooks/consent.json`; `check`/`confirm` are the only way to a `Confirmed`, the only input of `Runner::start(confirmed, log, on_run)`. `Runner::submit(&event)` queues the matching rules without waiting (64 pending, the oldest dropped and counted); a dispatcher task runs at most 4 at once, each with `env_clear` plus `PATH`/`HOME`/`LANG` and the `CUOTAI_*` data variables, the payload on stdin, the temporary directory as cwd, `kill_on_drop`, a timeout that kills and 16 KiB of captured output; each `Run` goes to `RunLog` (`runs.log`, no payload) and `on_run`. Dropping the runner aborts the dispatcher, which kills the running hooks.
  - **Editor and desktop (RF4):** `Document::read(path)` gives the rules as written (`RuleDraft`, valid or not; `None` when not TOML), their validation and the file's revision (SHA-256 of its bytes); `Document::save(path, revision, drafts)` validates with the same rules, refuses a file whose revision changed (`hooks.error.changed`) and rewrites it with `toml_edit`, keeping the tables (and comments) of rules kept by name. `Rule::sample(now)` builds a made-up event of the rule's first kind that passes its filters, marked `sample: true` (the payload field exists only then), which `Runner::submit_to(rule, &event)` runs for that rule alone; `RunLog::latest(n)` reads the log back, newest first, across the rotation. The desktop (`apps/desktop/src-tauri/src/hooks.rs`) keeps an `Integration` (switch from `desktop.json`, off by default; `Consent`; the runner and a `watch::Watcher`) that `reconcile`s what runs with the switch, the file beside the loaded TOML and the confirmations, and observes the `Export::from_cycle` of every `Backend::emit`; each of those re-reads the file before running any event, so changed rules stop until confirmed again and the main-window banner shows at the next state change.
- **`transport`**: a guard every credential-bearing request goes through (`providers::send`, `oauth::send_secure`): HTTPS is always allowed, plain HTTP only to loopback hosts (local OAuth callbacks and the contract tests' `wiremock` servers). Anything else fails closed with `query.insecure_transport` / `oauth_error.insecure_endpoint` before a byte is sent, and the URL is never reported.
- **`metrics`**: `classify_report` and `classify_metric` derive availability and consumption (`AccountClass` and `MetricState`). `binding(report)` picks the account's binding metric: among `Quota` metrics with a finite positive cap (`RateLimit` only when none qualifies), the exhausted one with the latest `resets_at` when the account is blocked (`blocked_until`; unknown when a return is missing), otherwise the smallest remaining fraction, ties to the shortest window then adapter order; non-`Ready` or unmeasured reports return `None`. `binding_ratio`/`cmp_binding` sort accounts with no value last, and `Binding::summary` emits the localized line (`binding.*`, nested `metric_window.*`).
- **`freshness`**: `age(checked_at, now)` and `assess(checked_at, interval, now)` classify a measurement as `Fresh` (up to 1.5× the account's effective interval), `Aging` (up to 3×) or `Stale`, with an injected clock; a measurement newer than `now` (clock went backwards) reads as age zero and `clock_adjusted` reports it.
- **`pace`**: `assess(metric, now, recent)` compares a `Quota` metric in a `window_5h`/`daily`/`weekly`/`monthly` window with a uniform pace until `resets_at` (calendar month for `monthly`; an RFC 3339 start in `period` wins when coherent): elapsed and expected fractions, `delta_points`, stage `Reserve`/`OnPace`/`Ahead`/`Exhausted` (±5-point band) with a `good`/`neutral`/`warn`/`bad` tone, and a linear projection (`source` `Average` since the start, or `Recent` slope over ≥ 3 `Point { taken_at, used }` samples in the last 2 hours or 10% of the window). Missing or non-finite data, a past reset and a window under 5% (or 10 minutes) old return `None`. `stage_label`/`outlook_label` emit `pace.*` texts.
- **`resets`**: `upcoming(config, reports, now, &prefs)` plans quota reset notices from the readings already taken, with an injected clock: a `Quota` metric with a future `resets_at` in a `window_5h`/`daily`/`weekly`/`monthly` window (`other` with `include_other`), filtered by `NotifyWhen` (`OnlyIfUsed` by default, `OnlyIfExhausted`, `Always`; a missing value is neither used nor exhausted), skipping accounts in `prefs.disabled`. Metrics of one account resetting within the same minute form one `ResetEvent` with `notify_at = resets_at − lead`. `ResetKey::same_reset` treats `resets_at` within 2 minutes as the same reset. Accounts are identified by `Account::key()` (`<provider slug>:<name>`); renaming an account gives it a new key.
  - **Delivery (PRD 0003 RF2):** `plan(config, readings, now, &prefs, &ledger)` (readings: a snapshot's reports or one `Option` per account) returns `due` — notices whose `notify_at` passed while the reset is at most `MISSED_GRACE` (10 minutes) old and that `Ledger` has not recorded, merged into at most one event per account — and `next`, the earliest notice ahead. `ResetEvent::notice(account, now)` writes the `resets.*` title and body (provider, account name and metric labels only). `Ledger` keeps SHA-256 digests of account key and label with `resets_at` and the notice date, drift-tolerant, pruned after `LEDGER_KEEP` (8 days), saved atomically to `<OS local data dir>/cuotai/notified.json`. The desktop backend (`apps/desktop/src-tauri/src/notify.rs`) owns the preferences in `desktop.json`, the `Notifier` trait over `tauri-plugin-notification` and `Notices::tick`; `Backend::run_notices` sleeps until `next` (at most 60 s) or a nudge from every view emission and preference change, and never queries a provider.
- **`oauth` and `login`**: `OAuthSession`, `OAuthConfig`, `OAuthLogin` and `TokenStore` manage credentials and renewal; `cuotai_core::login` exposes a cancellable, UI-independent driver with prompt/progress events and a staged commit between the vault and the TOML.

### Adding a provider

A new provider touches only the core; the TUI and the desktop app render its descriptors and reports generically.

1. Add the variant to `Provider` (`model.rs`: `label`, `slug`, `ALL`), the adapter under `providers/` and its dispatch in `lib.rs`.
2. **Declare its access descriptor (mandatory).** Add the arm to the exhaustive `match` in `access::classify` (level, credential class, scope, plan requirement, public evidence and the summary/reason texts), one arm per `params` value or login that changes the queried interface, and the `access.summary.<slug>` (plus `access.reason.<slug>` for `Unavailable`) ids in `locales/en-US.json` and `es.json`. The build fails without the arm, and the `access` tests fail without the texts or when `Unavailable` lacks a reason or `Official` lacks a documentation URL.
3. Regenerate the usage access matrix of [`providers.md`](providers.md) with `CUOTAI_REGENERATE_DOCS=1 cargo test -p cuotai-core providers_doc_matrix`; the same test without the variable fails while the document differs from `access::describe`. A new interface-switching param also goes into the `MODES` list of the `access` tests, which the matrix and the invariant tests walk.
4. Add the account fields in `account_edit.rs`, the credential help, an example to `cuotai.example.toml` and the `wiremock` contract tests.
5. A provider that reads usage with a **web session** (PRD 0016) also declares its slot in `user_session::descriptors` (accepted and required cookie names, the only hosts, delivery) and its adapter reads it with `providers::web_session` and sends it with `providers::send_session`; it enters only with evidence that the query is read-only and that the session alone is enough (vendor documentation, or a contract verified in 9router or a community client), recorded as the access descriptor's evidence. The `access` tests fail when a `UserSession` interface has no descriptor or a descriptor has no `UserSession` interface.

### Using it as a Rust library

```rust
use cuotai_core::{Config, Monitor};

async fn query(config: Config) -> Result<(), Box<dyn std::error::Error>> {
    let monitor = Monitor::new(config)?;
    let snapshot = monitor.refresh().await;
    println!("{}", serde_json::to_string(&snapshot)?);
    Ok(())
}
```

- `AccountClass` serializes as `"available"`, `"exhausted"` or `"unmeasured"`.
- `MetricState` serializes with the `state` tag: `{"state":"unmeasured"}`, `{"state":"exhausted","no_cap":true}` or `{"state":"available","ratio":0.25,"uncapped":false}` (when `uncapped` is `true`, `ratio` does not represent availability).
- Each `Metric` carries `kind` (`"quota"`, `"rate_limit"`, `"balance"`, `"credits"`, `"spend"` or `"usage"`) and `window` (`"window_5h"`, `"daily"`, `"weekly"`, `"monthly"`, `"other"` or `null`). The adapters assign these fields from the provider's contract; front ends must not infer them from `label` or `period`. The fields are additive to the `Snapshot` and to the CLI JSON.
- `account_edit::CredentialKind` serializes as `"env"`, `"profile"` or `"none"`.
- `Monitor::with_credentials(config, Arc<dyn Credentials>)` lets you inject a custom secret lookup (`Credentials::get` must be fast and non-interactive). `Monitor::with_oauth` shares the `OAuthSession` across queries.

### Internationalization (`Localized`)

Structured texts emitted by the core carry `Localized { id, params, fallback }`:

- The **core owns the catalog of the ids it emits**:
  `crates/cuotai-core/locales/{en-US,es}.json` (loaded through
  `include_str!` and `serde_json` behind a `LazyLock`). Every core id
  (field.*, native.*, login.*, credential_help.*, oauth.*,
  access.*, edit_error.*, query.*, note.*, remove_error.*,
  remove.kept.*, status.*, provider.*, binding.*, metric_window.*, pace.*, alerts.*, incident.*) lives in `en-US.json` and `es.json`
  with the same set of keys; `pt-BR` does not consult a catalog and uses
  the Portuguese `fallback` embedded in each `Localized`. Resolution
  (`Localized::resolve`, `cuotai_core::text::core_catalog`) follows the order
  exact locale → same language → `en-US` → `fallback`.
- The desktop app receives the core catalog through the Tauri command
  `core_catalog(locale)`, and `js/i18n.js` merges it under the UI catalog
  (`apps/desktop/ui/locales/*.json`); user packs (in
  `<user dir>/locales/<code>.json`) override both. Front ends **never match
  on text**: `t()` and `tl()` look the id up in the catalog.
- The TUI resolves the core's `Localized` values through `Localized::resolve` in the
  active locale (`CUOTAI_LANG`, default `pt-BR`); Ratatui's own captions
  (shortcuts, frames, ...) are outside the scope of RF8 and remain in
  Portuguese.
- `Report.notes` keeps Portuguese text for compatibility with CLI/JSON
  consumers; `Report.notes_l10n` accompanies the notes in the same order
  with structured ids and parameters (never containing tokens). Adding a
  language only means adding a catalog.

## Development and verification commands

Run from the workspace root:

```sh
cargo test --workspace
cargo clippy --workspace --all-targets -- -D warnings
cargo build --workspace
cargo fmt --all -- --check
```

For the desktop app (Tauri):

```sh
cargo test --manifest-path apps/desktop/src-tauri/Cargo.toml
cargo clippy --manifest-path apps/desktop/src-tauri/Cargo.toml --all-targets -- -D warnings
```

Dependency licenses, advisories and sources are checked with `cargo deny` (see [`CONTRIBUTING.md`](../CONTRIBUTING.md)).

### Continuous integration

[`.github/workflows/ci.yml`](../.github/workflows/ci.yml) runs on every push and pull request (PRD 0019, RF2). On Linux, macOS and Windows it runs the commands above for both workspaces: `cargo fmt --check`, `cargo clippy --all-targets -D warnings` and `cargo test`, with `--locked`. A separate Linux job runs `cargo deny` on both workspaces. Each job has a timeout, the token is read-only (`contents: read`), every action is pinned by commit hash, the workflow uses no secrets, and pull requests (forks included) run with `pull_request`, never `pull_request_target`. The `target/` cache is only written from `main`.

Platform coverage of the test suite:

| Area | Linux | macOS | Windows |
|---|---|---|---|
| Contract, OAuth, persistence, TUI and desktop logic tests | yes | yes | yes |
| Owner-only permissions (`0600`/`0700`) and symlink handling in `ConfigFile`, `last_config`, the model cache and the dev SQLite store | yes | yes | no (`#[cfg(unix)]`: Unix permission bits and symlinks) |
| Fake `aws` and `bl` command-line tools (`#!/bin/sh` scripts), the hook fixture scripts (`/bin/sh`), and the `cuotai --serve` and `cuotai --watch` binary tests stopped with `kill -TERM`/`-INT`/`-HUP` | yes | yes | no (`#[cfg(unix)]`) |
| OS credential vault (Keychain, Credential Manager, Secret Service) | not tested | not tested | not tested |
| Tray, notifications and opening the system browser | not tested | not tested | not tested |

Tests never touch the real vault, tray, notifications or browser: OAuth and account tests use an in-memory `TokenStore`, and the desktop tests exercise the backend without starting Tauri. Those surfaces need a packaged app and a manual check (PRD 0019, RF5.2). On Linux the desktop build needs WebKitGTK (`libwebkit2gtk-4.1-dev`). On Windows, `build.rs` embeds Tauri's Common Controls v6 manifest into every artifact so the test executables can load (tauri-apps/tauri#13419), and the bundle lists `icons/icon.ico`, which the Windows resource step requires.

### Test and verification scope

- **Contract tests (`wiremock`):** exercise pagination, cents/currency, overflow, incomplete schemas, billing filters, gross versus net consumption, balance versus spend, and missing or invalid credentials, without depending on an external network.
- **OAuth and vault tests:** cover callback/CSRF, denial, polling/`slow_down`/expiry, RSA/X25519/AES-GCM encryption, refresh-token rotation, per-account/provider isolation (for example, multiple Kiro accounts) and the staged commit.
- **Persistence and TUI tests:** validate editing and reordering in `ConfigFile` while preserving comments, `0600` permissions, rejection of symlinks and concurrent edits, and rendering of the dashboard and wizard.
- Simulated HTTP responses validate contracts and error handling, but they do not replace authorization and querying against real production accounts.
